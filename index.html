The problem

Anti-scam work is reactive. The hard part is the scam you haven't seen.

Singaporeans lost over S$900 million to scams in 2025. Most anti-scam tooling is reactive — defences get built after victims appear.

The hard part isn't catching a scam we've seen a hundred times. It's making sure no second victim falls to an attack vector we already understand — while staying ready for the ones we don't. And it's doing that with an AI you can actually trust: a classifier that hallucinates a scam category is worse than none — it points a victim the wrong way, with total confidence.

The system

Three components, one rule — the AI never has the last word.

A report comes in; the classifier reads it grounded in the taxonomy and validates every answer against it. Match something known → a checked classification. Match nothing → flagged novel, into human curation.

Proof

The trust layer — reasoning you can check.

The thesis in code: the LLM reasons; the knowledge base validates; nothing unchecked reaches the output. Every classification carries a _validation block, because the model's answer isn't trusted until it's checked — in four layers:

  • 1Shape — is the output even the right structure?
  • 2Vocabulary — every facet value must exist in the taxonomy. Catches a hallucinated value.
  • 3Referential integrity — every category & pattern ID must exist. Catches an invented ID.
  • 4Consistency — the answer can't contradict itself.

A real case. Input: "My mother got a call from someone claiming to be the police, saying her bank account was linked to money laundering — move your savings to a 'safe account' to avoid arrest." The complete, checked output:

Every classification carries that _validation block. The point is what happens when the model doesn't behave — invent a value or an ID, and it's flagged, not trusted:

How I know it works — and where it doesn't

Today the system passes its evaluation — 13 cases across three models, 13/13 on Claude. The useful part is how it got there. An early run mislabelled a rental scam as "e-commerce" — confidently, on both Claude models, at 91–95%. My validation didn't catch it: the model picked a category that was real, just not correct, and validation checks that a value exists, not that it's the right one.

So I did the research — checked the taxonomies the field uses (the US Federal Reserve's ScamClassifier, Singapore Police advisories), found rental scams are a recognised, distinct category my knowledge base was missing, added it with sourcing, and the case passed. The deeper problem it exposed — a model confident and wrong about a real category — sits at the top of my roadmap.

Human in the loop

The review console — built for an anti-scam analyst.

This is the part of the system closest to ScamShield's own work — their public 2025 updates describe building a dashboard to triage and label scam reports. So I designed the review surface for exactly that user: an analyst working the queue.

When the classifier flags a report as novel, it lands here rather than being force-fit into a wrong category. The analyst sees the report, the classifier's read, and the validation status, then decides. On approval, the system generates a draft taxonomy entry — which the analyst verifies against a real source before it enters the knowledge base. Nothing is added automatically; a human is always the gate.

Where it's going

Two jobs — prevent the second victim, then the first.

Prevent the second victim — recognise a known attack vector so no one else falls to it. This is built. Prevent the first victim — catch a brand-new scam before it claims anyone. This is the vision: surfacing scams from the wild, and a red-team that invents plausible variants and tests them against the live system before they appear at all.

Honesty

What it doesn't do — and which kind that is.

A system is only as trustworthy as its author's honesty about its limits. Two kinds, kept separate because they're different:

Deliberate scope decisions

  • Not deployed — a capability prototype, run locally; deployment is the next build's job.
  • Python, not the OGP stack — chosen for fast iteration; the TS/NestJS re-platform is the planned next prototype.
  • No retrieval/RAG — premature at this size; revisited when the KB grows or prompts get costly.
  • Review console is single-user, no auth — login, accounts, RBAC, and audit are production concerns for the officer-facing version.

Honest open gaps — each with a plan

  • Confident-but-wrong has no runtime check. Validation catches fabricated values/IDs, not a confident match to a real-but-wrong category (the rental case). → Plan: the embedding-distance ML trust check, independent of the model's own confidence.
  • is_scam false negatives exit silently. A wrong "not a scam" leaves no trace. → Plan: an is_scam confidence signal feeding a review route.
